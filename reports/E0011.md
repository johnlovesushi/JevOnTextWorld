  C3 and C4. Evaluation only: nothing was trained, the test sets were not used.

## Executor notes (part A)

### Differences from the issue

- **`scripts/check_games.py` and `walk` in `scripts/diagnose_history.py` were changed** (separate commit, with a
  CPU test; nothing in `jevtw/`). The walkthrough that TextWorld writes for games with two or three ingredients
  repeats `open fridge` before each ingredient, and on multi-room maps repeats `open <door>` when it passes a door
  again. The second `open X` is not among the admissible commands (X is open; `close X` is), and `walk` stopped
  there and reported a failure: 144 of 280 games in C2 and 192 of 280 in C4. `walk` now has
  `skip_redundant_open` (default off, so `build_sft_data.py` and the other callers behave as before);
  `check_games.py` turns it on, counts the skipped commands per game (`redundant_open`) and has `--strict-open`
  for the old behaviour. Only an `open X` whose `close X` is admissible is skipped; any other inadmissible
  command is still a failure. With it all 840 walkthroughs end in a win.
- C0 and C1 (one ingredient, one room) had no such command, which is why E0009 did not see this.

### Problems

- Generation is slow: about 19 s per game, 90 min per level on the login node.
- `scripts/build_sft_data.py` still uses the strict walk: on C2 or C4 it would drop about half of the games.
  Not needed for E0011 (no training); it matters if a later experiment trains with SFT on these levels.

### Reading

- The ladder separates the two factors as intended: C2 = more ingredients in one room (13–19 agent steps, no
  `go`), C3 = one ingredient on six rooms (8–13 steps, 1.4 `go` per game; 47 of the 280 games never leave the
  first room), C4 = both (13–51 steps, 4–5 `go` per game).
- C3 walkthroughs are only about one step longer than C1's (8–9): on its shortest path the six-room map adds
  little. What it adds for a policy is the chance to get lost, which part B measures (room loops).

### Decisions needed

1. Which H for part B (table above; proposal 38 / 30 / 102). **Decided by the user: 38 / 30 / 102.**
2. Whether `build_sft_data.py` should also skip the redundant `open` (not part of this issue).

## Executor notes (part B)

### Differences from the issue

- H = 38 / 30 / 102 was decided by the user (the issue's formula does not say which walkthrough length).
- One training seed per method, s17 for all three, with the checkpoint that E0010 selected for that seed. The
  E0010 validation results tie between the seeds of b and e, so the rule "best seed" selects nothing; I stated
  this choice on the issue before submitting.
- No group with reasoning: E0009 did not establish that reasoning helps, and the issue makes that group
  conditional on it.
- Two analysis scripts are used: the new `scripts/analyze_ladder.py` (with a CPU test) for the tables the issue
  asks for, and the existing `scripts/analyze_trap_free.py` for the kind of processing error. Nothing in `jevtw/`
  changed.

### Problems

- None in the jobs. `C4-base` took 10:37 against 5:23 for `C4-grpo` (see the note under the master table).
- `sftgrpo` adds no information beyond `sft` (identical episodes).

### Reading

- **C2 (more ingredients, one room): 0 / 80 for every model.** The sft model does what it learned on C1 for the
  first ingredient (takes it, cooks it, takes the knife in 56 of 80 episodes, cuts), then calls `prepare meal` in
  31 episodes while other ingredients are missing, and ends by cooking an ingredient a second time (42), with the
  wrong appliance (23) or cutting with the wrong verb (15). No episode reaches H: every loss is a processing
  error, within 23 steps. In the episodes I read, the single-ingredient routine is repeated on the same
  ingredient instead of moving on to the next one; I did not count this over all 80.
- **C3 (one ingredient, six rooms): sft 22 / 80, base 2, grpo 1.** Two things lose episodes for the sft model:
  walking (18 losses at H; loops in 30 episodes) and cooking the ingredient twice (29). The second also happens
  in games that need no `go` at all (7 wins in 24 such episodes, against 0.99 on C1, which has the same recipe
  size). I have no measured explanation for that; the C3 prompts differ from C1 by the exits listed in the room
  description and by the `go` options.
- **C4 (both): 0 / 80 for every model**, with the failures of C2 and C3 together; the sft model also eats an
  ingredient in 20 episodes.
- GRPO from the base model (group c of E0010) behaves like the base model on all three levels.

### Recommendation (suggestions only; nothing was started)

- The issue's rule — the hardest level where the SFT or RL model wins between 0.1 and 0.6 of the episodes, with
  no reasoning and `full` history — selects **C3** (sft 0.275). C2 and C4 are at 0 for every model, so on them a
  policy-gradient method has no win to learn from, whatever the start model.
- Caution for GRPO on C3 from the C1-SFT start: the wins are concentrated in few games (26 of 40 validation
  games have 0 wins in 2 episodes, 8 have 2). A group of 8 episodes of one game may often be all-loss or all-win;
  how often can only be measured with more episodes per game, which this issue did not ask for.
- Order of the levels suggested by these numbers: C1 → C3 → C2 → C4. C3 is reachable from C1 now. C2 needs the
  new skill "several ingredients", for which the C1 models have no partial success; it probably needs SFT on C2
  walkthroughs before any RL (this is a guess from 0 / 80, not something measured here). C4 last, as it needs
  both.

### Decisions needed

1. Accept C3 as the next training level, and with which start model (base, as E0010c, or the C1-SFT model)?
2. If SFT on C2 or C4 is planned: `scripts/build_sft_data.py` must skip the redundant `open` commands first,
   otherwise it drops about half of the games (part A). This is a code task, not part of this issue.
3. Whether to measure the within-game spread on C3 (more evaluation seeds per game) before a GRPO run there.
4. `sftgrpo` (E0010e) is the same policy as `sft` in practice; later ladders could drop it.
